# Подготовка рабочего сервера Rooms

## Автоматическая проверка

Из папки `server`:

```powershell
npm run check:deployment
npm run check:deployment -- --json
```

Команда читает текущие переменные окружения и `.env`, но не подключается к базе, банку, почте или S3, не отправляет сообщения и не меняет данные. Значения ключей, паролей и строк подключения в отчёт не попадают. Код завершения `1` означает, что запуск с реальными бронированиями/оплатой пока заблокирован; `0` не заменяет внешние проверки.

Шаблон безопасных рабочих настроек: `server/.env.production.example`. Это не готовая конфигурация: адреса и секреты намеренно пустые. Настоящие значения должны храниться в приватном окружении сервера, а не в репозитории. Для проверки отдельного файла можно задать `DOTENV_CONFIG_PATH`; уже заданные переменные процесса имеют приоритет.

В рабочем режиме сервер откажется запускаться без PostgreSQL, с отключённой двухфакторной защитой, тестовыми флагами безопасности или имитацией доставки уведомлений. Проверяются также независимость ключей, HTTPS, разрешённые источники запросов и настройки S3. Локальная разработка и браузерные тесты сохраняют свой прежний режим.

## Что пока блокирует оплату

В репозитории есть очередь фискальных чеков и демонстрационный адаптер, но **нет адаптера рабочей онлайн-кассы**. Поэтому пункт `fiscal-receipts` сейчас всегда имеет статус `FAIL`, независимо от заполненных переменных. Установка произвольного `FISCAL_RECEIPT_MODE=live` не заменяет реализацию. Нужно выбрать провайдера, реализовать его адаптер и проверить выдачу чека, возврат и повторную обработку.

Реквизиты банка и HTTPS-адрес также не доказывают, что эквайринг подключён: отчёт проверяет только наличие настроек и отсекает известный тестовый адрес Сбера. Рабочий адрес и доступы подтверждаются при подключении банка.

## Порядок развёртывания

1. Подготовить отдельное тестовое окружение, PostgreSQL и приватное S3-хранилище. Не использовать рабочие данные клиентов для экспериментов.
2. Настроить HTTPS-прокси перед API. Предпочтительно отдавать сайт и API с одного домена. Backend размещается отдельно от GitHub Pages: Pages не запускает Node.js и PostgreSQL.
3. Установить зависимости из lock-файла, выполнить проверку типов, тесты и сборку. Node.js: версия 24 или выше согласно `server/package.json`.
4. Настроить отдельные секреты, постоянную базу, S3, почту и банк. Выполнить `npm run check:deployment` и устранить ошибки, не отключая защиту.
5. Сделать резервную копию существующей базы перед обновлением, выполнить миграции и запустить сервер под диспетчером процессов. Не запускать демонстрационное заполнение рабочей базы.
6. Проверить HTTPS, вход и второй фактор, поиск окна, заявку, подтверждение и уведомление на отдельном тестовом аккаунте. Подтвердить, что S3 не отдаёт приватные объекты анонимно.
7. После подключения кассы проверить оплату и возврат в согласованном с банком режиме, включая повторы уведомлений и сверку сумм. Не считать автоматические тесты с памятью процесса подтверждением интеграции с банком.
8. Настроить внешний мониторинг и расписание резервного копирования, выполнить учебное восстановление в отдельную пустую базу. Зафиксировать ответственного за сбои и порядок отката версии.

После миграций выполнить `npm run db:check`: проверка истории обновлений не меняет базу. Сборка для размещения должна включать не только `server/dist`, но и `docs/database.sql`, `docs/migrations/*.sql` в исходной структуре каталогов. Они нужны для проверки контрольных сумм при запуске. Самостоятельно удалять записи из `schema_migrations` ради успешного старта нельзя.

Проверка не подтверждает физическое размещение данных, правовую готовность, права S3, работу внешних сервисов или восстановимость резервной копии. Эти пункты проверяются отдельно до приёма реальных клиентов.
