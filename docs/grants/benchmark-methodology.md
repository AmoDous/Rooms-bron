# Методика базового испытания алгоритмов Rooms

Статус: версия 0.1 для подготовки заявки. Методика отделяет проверяемые результаты от продуктовых обещаний и не подменяет пилот на реальных площадках.

## Цель

Получить воспроизводимую базовую линию, с которой позднее сравнивается разрабатываемый многокритериальный алгоритм интервального планирования Rooms.

## Набор данных

Текущий стенд содержит 120 синтетических запросов:

- 8 профилей расписания от свободного дня до фрагментированного графика;
- площадки с одним, двумя и тремя одновременно требуемыми помещениями;
- желаемое начало в 10:00, 12:00, 15:00, 18:00 и 21:00;
- продолжительность 2, 3 и 4 часа;
- рабочие часы, существующие брони и интервалы разной длины.

Каждый запуск фиксирует версию и SHA-256 хеш набора. Сценарии не содержат персональных данных и не выдаются за реальные заявки.

## Базовые стратегии

1. **Первое доступное окно** выбирает самое раннее допустимое начало.
2. **Ближайшее к желаемому времени** выбирает вариант с минимальным абсолютным сдвигом, при равенстве предпочитая более ранний.

Обе стратегии намеренно простые. Они не являются предметом заявляемой новизны и нужны как контроль для будущего алгоритма Rooms.

## Показатели

| Показатель | Определение |
| --- | --- |
| Выполнимость | Доля запросов, для которых существует хотя бы один допустимый вариант |
| Точное время | Доля выбранных вариантов, совпавших с желаемым началом |
| Возврат альтернативы | Доля выполнимых запросов без точного совпадения, для которых выбрано другое допустимое начало |
| Сдвиг | Абсолютная разница между желаемым и выбранным началом в минутах |
| Добавленные короткие интервалы | Изменение суммарной длительности свободных разрывов, которые короче минимальной брони помещения |
| Время расчёта | P50 и P95 времени обработки одного сценария на зафиксированном окружении |

Для нескольких помещений допустимым считается только общее окно. Показатель фрагментации суммируется по всем выбранным помещениям.

## Воспроизведение

Из папки `server`:

```powershell
npm run grant:benchmark
```

Команда создаёт:

- `docs/grants/evidence/synthetic-baseline.json` для машинной проверки;
- `docs/grants/evidence/synthetic-baseline.md` для паспорта проекта и обсуждения с экспертом.

Число повторов можно изменить через `ROOMS_BENCHMARK_ITERATIONS`. Для официального сравнения используется одинаковый компьютер, версия Node.js, набор сценариев и число повторов.

## Переход к пилоту

Перед включением целевых показателей в заявку необходимо:

1. Получить согласие минимум трёх площадок.
2. Преобразовать обезличенные календари в ту же схему ограничений.
3. Зафиксировать выбор сотрудника площадки и фактический результат заявки.
4. Сравнить минимум три подхода: первое окно, ближайшее время и алгоритм Rooms.
5. Рассчитать доверительные интервалы и отдельно показать результаты по типам площадок.
6. Не смешивать синтетические, исторические и проспективные данные в одной цифре.

### Воспроизведение пилотной базовой линии

После заполнения и ручной проверки трёх CSV-файлов сначала запускается безопасный импорт, затем расчёт двух базовых стратегий:

```powershell
npm run grant:pilot-benchmark -- --rooms <rooms.csv> --blocks <blocks.csv> --requests <requests.csv> --output ..\docs\grants\evidence\pilot-baseline-01
```

Расчёт восстанавливает календарь отдельно для каждого запроса на момент `created_at`. Блок занятости учитывается, только если его `recorded_at` не позже запроса и `released_at` отсутствует либо наступает после запроса. Так исключается утечка будущей информации в исторический эксперимент.

Сначала проверяется согласованность реконструкции с полем `exact_start_available`. Низкое совпадение означает проблему происхождения или полноты данных; показатели стратегий в этом случае не используются как доказательство. В отчёте отдельно фиксируются запросы сверх вместимости, будущие и уже снятые блоки, совпадение с историческим выбором сотрудника и SHA-256 исходного набора.

## Ограничения текущей версии

- стенд пока не оценивает цену, дополнительные услуги и вероятность подтверждения;
- наличие альтернативы не означает, что причина выбора понятно объяснена пользователю;
- синтетические профили не доказывают рост выручки или загрузки;
- замер производительности зависит от оборудования;
- эффект алгоритма Rooms появится только после реализации целевой функции и сравнения на пилотных данных.
- версия пилотного восстановления предполагает, что `recorded_at` и `released_at` площадки заполнены достоверно; без истории изменения календаря ретроспективное сравнение ограничено.
