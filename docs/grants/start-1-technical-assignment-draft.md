# Проект технического задания на выполнение НИОКР

Статус: черновик версии 0.1. Подготовлен по методическим рекомендациям ФСИ, согласно которым результат должен быть конкретным, измеримым, проверяемым и достижимым за 12 месяцев. Перед подачей документ переносится в форму новой очереди «Старт-1» и согласовывается с научным руководителем.

## 1. Наименование НИОКР

Разработка программного модуля многокритериального интервального планирования загрузки многокомнатных площадок с объяснимым выбором альтернатив бронирования.

## 2. Цель

Разработать и экспериментально проверить метод построения и ранжирования допустимых вариантов бронирования одного или нескольких помещений при динамических ограничениях, уменьшающий отклонение от запроса клиента без избыточной фрагментации оставшегося расписания.

## 3. Назначение результата

Результат предназначен для использования в цифровых сервисах бронирования помещений и внутренних системах площадок: караоке с отдельными комнатами, детских центрах, лаунджах, банкетных площадках и других объектах, где оплачивается время использования помещения.

Модуль получает обезличенное описание ресурсов, расписания и запроса, возвращает допустимые варианты, ранжирует их и объясняет основные причины выбора. Контактные и платёжные данные для расчёта не требуются.

## 4. Исходные данные

Модель должна поддерживать:

- от 1 до 20 помещений одной площадки;
- отдельные и совместно используемые помещения;
- вместимость, тип и набор возможностей;
- рабочие часы с переходом через полночь и исключения по датам;
- длительность бронирования от 60 до 720 минут;
- минимальную длительность и шаг начала 15, 30 или 60 минут;
- буфер подготовки и уборки от 0 до 120 минут;
- активные брони, временные удержания, ручную и техническую занятость;
- дополнительные услуги и ограничения их доступности;
- желаемое время, допустимый диапазон сдвига, количество гостей и ценовой предел.

Предельные значения являются проектными и уточняются после обследования пилотных площадок.

## 5. Требования к научно-техническому результату

### 5.1. Формальная модель

Должны быть определены:

1. Множество ресурсов и интервальных ограничений.
2. Правила допустимости назначения одного и нескольких помещений.
3. Целевая функция не менее чем из четырёх нормированных компонент: отклонение от желаемого времени, соответствие помещения, стоимость и изменение фрагментации расписания.
4. Способ задания весов и обязательных ограничений.
5. Правила разрешения равнозначных вариантов, обеспечивающие повторяемость результата.

### 5.2. Алгоритмический модуль

Модуль должен:

- построить множество допустимых вариантов в заданном горизонте;
- исключить пересечения с каждым видом занятости и учесть буферы;
- поддержать одновременный подбор нескольких помещений;
- рассчитать компоненты целевой функции для каждого кандидата;
- вернуть до 10 ранжированных вариантов;
- для каждого результата вернуть вклад критериев и факторы, исключившие точный запрос;
- обеспечивать одинаковый порядок результатов при одинаковом входе и настройках.

### 5.3. Программный интерфейс

- вход и выход описываются версионированной JSON Schema и OpenAPI;
- некорректные и противоречивые данные отклоняются с машиночитаемым кодом ошибки;
- результат содержит версию алгоритма, версию параметров и идентификатор набора ограничений;
- модуль не должен требовать персональных данных клиента;
- интеграция с экспериментальным API Rooms не изменяет серверный расчёт цены и транзакционную защиту от пересечений.

## 6. Проектные показатели приёмки

Значения ниже предварительные. Они утверждаются только после базового эксперимента на обезличенных данных и проверки техническим руководителем.

| Показатель | Требование | Способ проверки |
| --- | ---: | --- |
| Нарушения жёстких ограничений | 0 | Автоматическая проверка каждого выданного результата |
| Полнота поиска при дискретном шаге | 100% относительно исчерпывающего эталона на контрольном наборе | Сравнение множеств допустимых вариантов |
| Возврат допустимой альтернативы при её наличии | не менее 99% | Синтетический и пилотный наборы |
| Улучшение сводной целевой функции | не менее 10% относительно лучшей простой стратегии | Парное сравнение на одинаковых запросах |
| Снижение новых коротких интервалов | не менее 15% при сопоставимом отклонении по времени | Сравнение с «первым окном» и «ближайшим временем» |
| P95 расчёта одного запроса | не более 500 мс для 20 помещений и горизонта 31 день | Зафиксированное тестовое окружение |
| Объяснение результата | 100% возвращённых вариантов содержат оценки критериев и причины сдвига | Контрактные тесты API |
| Устойчивость к параллельным запросам | отсутствие конфликтующих подтверждённых броней | Нагрузочный и транзакционный тест |

Понятность объяснения для пользователя оценивается отдельно и не подменяется фактом наличия технического поля в API.

Предварительный программный задел по показателю полноты: версия 0.1 совпала с независимым перебором на 300 малых синтетических задачах и 1 831 допустимом варианте. Это не заменяет приёмочный набор НИОКР: его границы, генератор и эталон должны быть утверждены отдельно и не использоваться для настройки алгоритма.

## 7. Методика испытаний

1. Модульные и генеративные тесты жёстких ограничений.
2. Сравнение с исчерпывающим алгоритмом на ограниченных наборах.
3. Сравнение трёх стратегий на одинаковых запросах: первое окно, ближайшее время, алгоритм Rooms.
4. Для ретроспективных данных — восстановление календаря на момент поступления запроса по времени создания и снятия каждого блока, без использования будущей информации.
5. Отдельные срезы по типу площадки, числу помещений, заполненности и горизонту бронирования.
6. Нагрузочное испытание в фиксированном окружении.
7. Проспективный пилот минимум на трёх площадках без передачи персональных данных клиентов.
8. Статистическая оценка различий и документирование неудачных сценариев.

## 8. Состав результатов

1. Отчёт о формальной модели и результатах патентно-информационного поиска.
2. Версионированная библиотека алгоритма с исходным кодом.
3. Экспериментальный API и интеграция с прототипом Rooms.
4. Синтетический и обезличенный пилотный наборы с паспортами происхождения.
5. Методика и программные средства испытаний.
6. Промежуточный и заключительный научно-технические отчёты.
7. Руководство разработчика и описание эксплуатации модуля.
8. Комплект материалов для регистрации программы для ЭВМ.

## 9. Что не относится к НИОКР

- рекламное продвижение и закупка трафика;
- наполнение каталога фотографиями и текстами;
- обычная вёрстка публичных страниц;
- подключение конкретного платёжного провайдера и онлайн-кассы;
- юридическая регистрация предприятия;
- текущее сопровождение инфраструктуры и пользовательская поддержка.

Эти работы могут быть нужны бизнесу, но не должны маскироваться под научно-технический результат гранта.

## 10. Открытые вопросы до подачи

- утвердить математическую запись целевой функции;
- подтвердить предельные параметры на интервью площадок;
- выбрать фиксированное окружение нагрузочных испытаний;
- обосновать пороги 10%, 15% и 500 мс базовыми измерениями;
- определить состав команды и владельца каждого результата;
- проверить соответствие формулировок положению новой очереди.
