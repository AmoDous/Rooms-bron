# Эксплуатация Rooms

Этот документ описывает минимальный порядок контроля пилотного сервиса. Он не содержит паролей, ключей и адресов production-инфраструктуры.

Перед развёртыванием выполнить `npm run check:deployment` из `server`. Порядок запуска и известные блокеры описаны в [подготовке рабочего сервера](deployment-readiness.md).

## Состояние сервиса

- Публичный `GET /health` показывает доступность API и типы подключённых хранилищ.
- Закрытый `GET /v1/admin/operations/health` доступен только администратору и возвращает агрегаты по запросам, уведомлениям, чекам и возвратам.
- В админке Rooms эта сводка отображается в блоке «Состояние сервиса» и не содержит персональных данных, текста сообщений, банковских реквизитов или секретов.
- Ответ административной проверки имеет `Cache-Control: no-store`.

## Что требует реакции

Реагировать сразу:

- API или PostgreSQL недоступны;
- появились ответы API со статусом `5xx`;
- возврат или фискальный чек имеет статус `failed`;
- очередь уведомлений не уменьшается либо содержит `failed`;
- production работает с `demo`-оплатой, памятью процесса или локальным хранилищем фотографий;
- время ответа заметно выросло относительно обычного уровня.

Перед пилотом настроить внешние уведомления минимум на такие пороги:

- API недоступен две проверки подряд с интервалом 1 минута;
- доля `5xx` выше 2% за 5 минут;
- любой возврат в `failed` дольше 5 минут;
- любой чек в `failed` дольше 15 минут;
- уведомление находится в очереди дольше 10 минут;
- свободное место PostgreSQL или S3 ниже 20%.

## Резервное копирование PostgreSQL

### Проверка версии базы

Перед запуском или обновлением сервиса выполнить из `server`:

```powershell
npm run db:check
npm run db:check -- --json
```

Проверка подключается к настроенной PostgreSQL в транзакции только для чтения. Она сверяет журнал всех 20 обновлений и контрольные суммы SQL-файлов. Данные клиентов и структура базы не меняются. Код `0` означает совместимую историю обновлений, `1` — незавершённые обновления, расхождение истории или ошибку проверки. Это не полная проверка структуры: ручные изменения таблиц вне журнала миграций она не обнаруживает.

При старте API выполняется такая же проверка. Сервис не начнёт принимать заявки, если обновления не применены, известные SQL-файлы изменены после применения, в истории есть пропуски или база содержит обновления от неизвестной этой версии сервера сборки.

При `pending` сначала создать резервную копию, затем выполнить `npm run db:migrate`. Скрипт использует одну выделенную связь с базой и блокировку от второго одновременного запуска. Каждый шаг выполняется в своей транзакции; после сбоя можно исправить причину и повторить запуск, уже завершённые шаги будут пропущены.

При `changed`, `unexpected` или `outOfOrder` не удалять строки журнала и не подменять контрольные суммы. Сначала проверить версию развёрнутого приложения и состав SQL-файлов. Контрольные суммы учитывают исходные байты, включая окончания строк: SQL-файлы должны переноситься в неизменном виде. Обычный откат кода на версию, не знающую новых миграций, будет остановлен этой проверкой; порядок отката нужно заранее согласовать.

### Создание копии

1. Делать ежедневную полную копию и хранить не менее 14 последних копий.
2. Шифровать архивы и хранить их отдельно от сервера приложения.
3. Ограничить доступ отдельной сервисной учётной записью только для резервного копирования.
4. Не помещать архивы, `.env`, ключи и дампы в Git.
5. Не реже одного раза в месяц проверять восстановление на отдельной базе.

Пример создания дампа для администратора инфраструктуры:

```powershell
cd server
npm run db:backup
```

Скрипт не передаёт пароль в аргументах процесса, сначала пишет временный файл, а после успешного завершения сохраняет архив и JSON-метаданные с размером и SHA-256. По умолчанию копии находятся в `server-data/backups`, не попадают в Git и хранятся 14 дней. Каталог и срок задаются через `BACKUP_DIR` и `BACKUP_RETENTION_DAYS`.

После каждой копии нужно выполнить безопасную проверку целостности. Она сверяет размер, SHA-256, читаемость архива и наличие основных таблиц, но ничего не записывает в базу:

```powershell
npm run db:backup:verify
```

Для проверки конкретного архива задаётся `BACKUP_FILE`. На Windows Rooms автоматически ищет инструменты PostgreSQL 15–18; на сервере можно задать `POSTGRES_BIN`, `PG_DUMP_PATH` и `PG_RESTORE_PATH`.

Полное учебное восстановление выполняется администратором инфраструктуры только в отдельной пустой базе. После него нужно запустить миграции, тестовый вход, поиск свободного окна, создание и отмену тестовой брони. Production-базу для учебного восстановления не использовать.

## Действия при инциденте

1. Зафиксировать время, затронутые функции и идентификаторы запросов из журналов.
2. Ограничить повреждённый сценарий, не удаляя журналы и доказательства.
3. Отозвать скомпрометированные ключи и активные сессии.
4. Проверить целостность PostgreSQL, очередей, S3 и платежей у провайдера.
5. Восстановить работу и проверить повторные операции на идемпотентность.
6. Отдельно определить, затронуты ли персональные данные и требуется ли уведомление Роскомнадзора и пользователей.
7. Записать причину, масштаб, действия и меры против повторения.

Юридические сроки и формулировки уведомлений перед production-запуском должен проверить профильный специалист по 152-ФЗ.
